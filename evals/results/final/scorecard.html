Methodology and limitations

  • Dataset: 16 PRs (3 clean) with 22 expected issues, each reviewed against a real git repo. Issues were planted on purpose; clean PRs have none, so any finding there is a false alarm.
  • Runs: 3 runs per arm, cache off; arms: baseline, pipeline, pipeline_no_verifier, pipeline_no_context. Precision, recall and F1 are pooled over PRs in each run, then averaged over runs (sample std; with a handful of runs treat it as a rough indication).
  • Models: specialists gpt-6.1-terra, baseline gpt-6.1-terra, verifier gpt-6.1-sol, judge gpt-4.1.
  • Scoring: the judge decides only whether a finding describes the same problem as an expected issue; code checks the location and assigns matches one-to-one. A finding the pipeline dropped is not scored.
  • Judge agreement: the judge (gpt-4.1) agrees with the hand-labeled answer on 6 of 6 test cases.

Limitations

  • Synthetic data. The PRs are written, not collected from real projects. They are probably tidier and more clearly wrong than real bugs.
  • Single repo. Everything is one small Python service. Results may not carry over to other languages, sizes or codebases.
  • Same author for the dataset and the checklists (D6). The same author wrote the planted issues and the specialists' checklists, so both arms are favoured. The baseline therefore gets the same checklist, which keeps the comparison fair on checklists but cannot remove that shared bias.
  • Judge model choice (D8). The judge (gpt-4.1) is a different model from the verifier (gpt-6.1-sol) and from the specialists, so it should not favour either arm (D8). It is still a model and can be wrong; the agreement check above is the evidence for how often.
  • Small sample. 22 expected issues and 16 PRs: one issue moves recall by 5 points. Model output also varies between runs.
